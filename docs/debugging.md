# Unattended engine debugging

Start with a case that reaches the failing code, proves it reached it, and exits on its own. For the open Last Stand tasks, build the small fixture first and use the full map once the mechanism is understood. [Decision and research](decisions/ADR-0026-unattended-engine-debugging.md)

## Debugging loop for DeepSeek

1. Read [state](state.json), the [task board](tasks/BOARD.md), the relevant issue, and the retained manifest. Write down the symptom as an observable predicate and name the events that prove the fixture exercised it. Search for an existing fixture and use its recorded command and inputs when they still match.
2. Freeze the control before editing. Record the executable SHA-256, matching PDB if available, source revision and patch hashes, game data and loaded script identity, map, slot/controller, seed, arguments, options, and effective debug switches. Confirm the running PID belongs to the selected executable. Verify fixture capabilities on that build at startup. Keep the launch announcement, isolated mutable copy, and native 1920×1080 for graphical runs.
3. Pick the shortest case that reaches the real code. Start with a native fixture for a local invariant, a scripted skirmish for AI/commands and object lifetime, or a graphical fixture for drawing, shroud visuals, input or focus. Use strict replay only within a demonstrated synchronized window and only when its target events are present. Keep a simulated human slot where the code needs player ownership; issue its orders programmatically.
4. Run the control through the event, with a ready deadline, a progress watchdog, and a total deadline. Verify map and initialized state first, then require the expected object/module/command or count within a case-specific tick window. An empty log, missing unit, idle AI, or early divergence invalidates the run. Diagnose coverage or setup before touching the suspected engine code. Stop once the predicate or its bounded observation window is complete.
5. Capture the first discrepancy. Narrow the tick window and log the smallest set of decision inputs and outputs. For a replay mismatch, compare setup inputs at tick 0, then the earliest divergent checkpoint, subsystem and object/command. Keep the first mismatch even if recording continues for exploration. A sync-bypassed run is diagnostic evidence; its later ticks cannot establish route parity or a fix.
6. Change one behavior at a time. On a fix, keep a failing control and verify the candidate reaches the same trigger and passes its expected outcome. For an optimization, compare semantically equivalent control/candidate cases before alternating timing runs. If the behavior intentionally changes, assert that delta and guard unrelated behavior. Compare timings in the same workload phase with the same render mode, options and minimal probes. Record the event counts, first difference and run spread.
7. Report the command, build, coverage, expected/observed result, first divergent tick or fault, one evidence link and the next hypothesis. Escalate to a person only for an input or device state the fixture cannot recreate. Ask for the smallest missing observation, such as a saved state or a short visual confirmation.

## First three fixtures

These are specifications for implementation. The board and state record the current runtime validation.

| Case | Workload and coverage | Verdict |
|---|---|---|
| **T-117 deploy guard** | Extend the T-081 pattern. Spawn a China Nuke Cannon for a real human slot, assert the deploy module and stage a visible hostile target that can exercise the guard chase. Issue guard and wait for the deploy transition. Drive the actual chase/move path with its real command source, including the packing/unpacking boundary. Then issue Stop followed by an ordinary move. Record module/state, input source, deploy/pack transitions, position, and shot frame. | Control must show the reported pack/chase at least once in the relevant case. Hold-only candidate stays deployed during the guarded chase, fires at an in-range target, then moves after Stop. If the chase or shot setup was never reached, the result is inconclusive. Keep deployed avoidance (allied route around blocker) and long-range vision (effective sight, guard radius and weapon-set refresh) as separate cases. |
| **T-116 formation start** | Recreate the recorded bad leader start in a footprint with a clear, unpinched member in the goal's effective zone. Assert the leader/alternate cells, zones, actual group order, and `zone_mismatch` on the control. Add a single-member case and a case where all alternates are invalid. Hold T-117 switches off for isolation. | Candidate selects the expected alternate, dispatches the route, and members move. The no-valid-alternate cases take the normal failure path. For scale evidence, run Last Stand with scripted pressure through normal player orders and predeclare the minimum formation count and target failure signature derived from the live baseline. Stop the run as invalid if it never produces the expected workload. |
| **T-118 occupant cache** | Use one source revision and a diagnostics-only cache/reference switch, or builds that differ only by the cache patch. Start with T-117 off. Exercise fixed occupancy, move/relocate and replace, then destroy and recycle the cell info; include reset or save/load if it rebuilds this map. Run queries across the actual removal phases. Before dereferencing the cached pointer, compare it with the fresh ObjectID lookup and log tick, cell, ID and lifecycle event. | No stale cache at a usable lookup point, and width answers, routes and expansions match. Confirm the oracle catches a deliberate stale entry in a defensive fixture. Then measure `ZH_PF_FRAME` and frame attribution on matched workload with the oracle off. Comparing `t116-path-cache.exe` to `t116-leader-zone.exe` alone does not establish a cache-only effect because the builds have different upstream changes. |

## Instructions for building the tools

1. **Extend the engine fixture hook.** Keep it development-only, opt-in and gated to local singleplayer. Use the existing match setup, game logic tick and normal command dispatch. Scenario definitions should name the map, seed, slots, template and coordinates, scheduled actions, required coverage and assertions. Start with fixed typed actions for spawn, guard, move, stop and observe. Validate templates/modules and passability up front. Use logic ticks for scheduling, real monotonic time for the watchdog. Let the case return a result and exit cleanly. Qualify each fixture in the mode it will use because headless startup and graphical object creation may differ.
2. **Extend the launch wrapper around one case at a time.** Use existing mutable-copy safety and engine identity helpers. Validate resolved paths, pass an explicit child environment and record only the relevant options. Match real AI/human slot metadata and verify any parsed switches via a versioned readiness record. Lock the working copy and user-data profile while they are in use. Own the child process and its helpers, time out startup/progress/total separately, and restore any staged changes in teardown. If killed during staging, recover from a small journal before another run. Keep test-only binaries out of patcher packaging.
3. **Return a machine-readable verdict.** Write an incremental heartbeat/current logic tick and a versioned result containing case and build identity, expected and observed coverage, verdict, first failing assertion or divergence, child exit code, and paths to logs. Use `pass`, `assertion_failed`, `invalid_fixture`, `diverged`, `crash`, `timeout`, and `infrastructure_error`. Only `pass` returns zero. Flush readiness, key events and final results. Keep a bounded event tail and opt-in detailed traces for the chosen tick window. Keep stdout short enough to paste into a handoff.
4. **Prove the runner fails correctly.** Exercise pass, assertion failure, wrong map/template/switch, zero target events, divergence, early crash and stall. Run the same control twice and compare the covered tick/event sequence. Verify cleanup after success and failure and confirm evidence survives a killed case. Start with the T-117 short fixture as the first end-to-end demonstration. Add a longer pressure scenario only after its coverage check can fail fast.

Keep commands and summaries under the existing experiment manifest. See [repository instructions](../AGENTS.md) for evidence tags and scope. For lifecycle faults, a small compatible MSVC AddressSanitizer build is an optional second check; the occupancy oracle remains necessary because reuse inside an engine pool may escape allocator-based detection. [MSVC ASan](https://learn.microsoft.com/en-us/cpp/sanitizers/asan?view=msvc-170)
